# D1 identity implementation plan

**Goal:** Deliver the D1 platform and identity workstream without editing D2–D4 modules.
**Architecture:** Follow the approved architecture, database and API contracts. Supabase owns Auth; current active database profiles own authorization. Server-only services own privileged calls and PostgreSQL transactions serialize identity writes.
**Tech stack:** Next.js 16.4.3, TypeScript, Supabase SSR, Vitest, PostgreSQL 17.
**Spec:** `docs/architecture.md`, `docs/database-schema.md`, `docs/api-contracts.md`, `docs/team-workstreams.md` and the user's D1 implementation request.

## Constraints and ownership

Only D1 paths. Preserve starter styling/assets and other developers' code. No credentials in Git. No hosted changes until the human designates a development project; create a dedicated project only in their chosen organization. No main pushes, history rewrites, destructive rollback or financial workflow implementation.

Current readers/writers: starter UI only; Auth bootstrap and baseline read policies are SQL targets. New readers: cookie-bound session clients and server identity services. New writers: Auth SDK, authorized identity RPCs. Keep baseline tables and signatures compatible. Expand with RPCs/tables, verify, retain schema on application rollback; no contraction.

## Review focus

- Revoked/disabled users with unexpired cookies must fail on each operation.
- Browser input and metadata cannot choose privileges or bypass optimistic concurrency.
- Concurrent role changes cannot remove all active admins.
- Invite delivery and promotion can fail independently; retries must be safe and observable.
- Refreshed cookies and customer data cannot enter shared caches; callback paths cannot redirect off-site.
